# Memory

`src/memory/` owns each persona's memory store and the §4 three-tier
render. The on-disk shape is documented in `docs/storage.md`; this
file documents the *behavior* — entry shape, append rules, render
budgets, and the contract that **status is never auto-mutated**.

## Entry shape

```ts
interface MemoryEntry {
  id: string;          // slug derived from summary/text on append
  date: string;        // ISO timestamp at append time
  summary: string;     // ≤240 char headline; ALWAYS rendered
  text: string;        // body — rendered in Core/Active when in budget
  status: "active" | "faded" | "forgotten";
  details?: string;    // ≤5 MB; NEVER inlined; via get_memory_details(id)
  kind?: string;       // free-form: "decision" | "gotcha" | "handoff" | "fact" | "log"
  summoner_username?: string;  // populated when appended in a summon-spawned session
  core?: boolean;      // true → Core tier, subject to 10 KB middle-out cap
}
```

Field renames from summon-mcp:

| summon-mcp     | pantheon  | reason                                  |
|----------------|-----------|------------------------------------------|
| `pinned: true` | `core: true` | §4 / §11b decision; no `pinned` fallback. |

The previous flat `text` field becomes the three-tier
`summary` + `text` + `details?` split. Pantheon code reads `core`
only — there is no compatibility path. Legacy summon-mcp data is
imported by Leandro's private one-shot script before pantheon goes
live.

## Append contract

`appendEntry(paths, username, input)` requires `text` (`missing_text`
on empty/absent). `summary` is optional and derived via
`deriveSummary(text)` when omitted: first non-empty line, headings
stripped, sentence-aware truncation, ellipsis fallback. Provided
summaries longer than 240 chars are rejected (`summary_too_long`)
rather than silently truncated.

`details` is optional. The 5 MB cap is enforced at TWO boundaries
(defense in depth):

1. `appendEntry` / `updateEntry` reject `entry_too_large` before any
   write reaches disk.
2. The store mutator runs the same check just before persistence so a
   programmatic bypass of the API would still fail.

`id` is generated by slugifying the summary (or text fallback). On
collisions the slug gains a `-2`, `-3`, … suffix.

`summoner_username` is the runtime-attribution field (§6 LOW). The
identity layer's session record knows whether the current session was
spawned by a `summon` call and exposes the summoner's handle; the MCP
handler passes it down to `appendEntry`.

## Status mutation

The `MemoryStatus` field changes ONLY through:

- `fadeEntry` / `forgetEntry` (explicit user calls).
- `recallEntry`, which flips faded → active (the "expand and revive"
  user intent).
- `updateEntry({ status })` — for completeness; surfaced as
  `update_memory({ status })` in the MCP layer.

Render-time budget enforcement does not call any of these. §4 is
explicit on this point: collapse is a **render-time** transformation,
status stays put.

## Render

`renderForPrompt(paths, username, options?)` returns
`{ text, warning }`. The text is multi-section; the warning is non-
null only when Core collapse fired (or Core is over 10 KB even with
nothing collapsible left).

### Tier table (per §4)

| Status     | core  | within budget | render shape                       |
|------------|-------|---------------|-------------------------------------|
| active     | yes   | yes           | Core, full text                     |
| active     | yes   | no            | Core, summary-only inline (collapsed) |
| active     | no    | yes           | Active, full text                   |
| active     | no    | no            | Active, summary-only inline (collapsed) |
| faded      | yes   | yes           | Core, full text, marked "(faded)"   |
| faded      | yes   | no            | Core, summary-only, "(faded)"       |
| faded      | no    | —             | Index synopsis                      |
| forgotten  | —     | —             | Hidden (unless `include_forgotten`) |

### Core (10 KB middle-out)

Sort core entries ascending by date. Always keep the oldest
`CORE_HEAD_KEEP=2` and newest `CORE_TAIL_KEEP=4` as full text — they
anchor the timeline. The middle is the budget-elastic region:
collapse middle entries from the center outward (closest-to-center
first) until the total full-text byte count fits in 10 KB.

If the head + tail alone exceed the budget the warning surfaces but
no head/tail entry is collapsed — auto-fading user-pinned core
entries is explicitly forbidden.

### Active (8 KB byte budget, oldest-first collapse)

Sort active non-core entries ascending by date. Render newest first
in the output. Walk newest → oldest, accumulating byte sizes; once
the running total would exceed the 8 KB budget, switch the older
entries to summary-only inline. The newest entry is always kept full
even if it alone exceeds the budget (otherwise the agent has no body
text at all).

### Index (faded non-core)

Sorted **date descending** (newest at top, per Leandro). After 50
entries a footer surfaces:
`+N more — call \`list_memory\` to filter`.

### Forgotten

Hidden by default; `include_forgotten: true` adds a `═══ HIDDEN ═══`
section. No tier-aware shaping — straight index lines.

## list_memory

`listIndex(paths, username, filter?)` returns the cheap index shape:

```ts
interface MemoryIndexEntry {
  id: string;
  date: string;
  status: MemoryStatus;
  core: boolean;
  summary: string;
  size_kb: number;
  has_details: boolean;
  kind?: string;
}
```

Filters compose: `status` (default `"active"`; pass `"all"` to span
every status), `core`, `kind`, `since` (ISO date lower bound),
`filter` (case-insensitive substring across summary + text). Sorted
date-descending.

## Edge cases

Two tier behaviors aren't spelled out in §4 but are the right read,
both confirmed with semaphoremole:

- **Active tier — newest entry is always rendered full.** When a
  single entry exceeds the 8 KB byte budget, it still renders in
  full. Collapse only applies to *additional* entries past the
  budget. Otherwise the agent has zero body content to work from,
  which fails the "useful at startup" goal harder than the byte cap
  fails it.
- **Core tier — head + tail with no middle never collapses.** When
  the core list has `entries.length ≤ CORE_HEAD_KEEP + CORE_TAIL_KEEP`
  (six or fewer entries), there is no middle region; nothing is
  collapsed. If the head + tail alone exceed 10 KB the warning
  shape becomes `⚠ Core total (X.X KB) exceeds 10 KB cap` so the
  agent knows trimming is needed but their core entries themselves
  weren't touched. Auto-fading user-pinned core content is
  explicitly forbidden (§4 / §11b).

## Snapshots (§6 LOW)

Labeled snapshots of the persona's memory store live as parallel
JSON files at:

```
~/.local/share/pantheon/personas/<handle>/memory.snapshots/<label>.json
```

`snapshot_memory({ label })` writes the current store via
`writeJsonAtomic`. `restore_memory({ label })` reads the snapshot
back via `mutateStore`, replacing the main store atomically.
`list_snapshots({ username? })` returns
`{ label, size_bytes, created_at }` rows sorted newest-first.
`delete_snapshot({ label })` removes a single snapshot
(idempotent — returns `deleted: false` for unknown labels).

**No auto-cleanup.** Snapshots count toward disk usage and
persist until explicitly deleted. The implicit assumption: an
operator who took a snapshot intends to keep it until they say
otherwise. A future `pantheon doctor` check could surface
"persona X has N snapshots totaling Y MB" but doesn't auto-prune.

Labels match `/^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$/` — alphanumeric
with `_ . -`, leading alphanumeric, ≤64 chars. Reserved
characters (`/`, whitespace) are rejected.

`restore_memory` is **destructive** to the main store: the
overwrite is reversible only by another snapshot taken before
the restore. The intended pattern is "snapshot → risky edit →
keep or restore".

## Concurrency

All store writes route through `mutateStore` → `mutateJsonAtomic`,
which uses the `(mtimeNs, ino, size)` fingerprint guard from
`docs/storage.md`. Multiple sibling incarnations writing to the same
shared memory file get conflict-detection retry; per-attempt cost is
one extra `stat`. Single-instance use never trips a retry.
